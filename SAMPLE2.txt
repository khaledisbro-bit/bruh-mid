  THE GATE, RUN
  -------------
  The build was run end to end under the offline stand-in, with the slice the
  file keys itself checked against its own tag.

    slice 3's tag over its closed bytes          AGREES
    the key the gate then built                  902766382:38066988:882264298
    slice 4's tag under that key                 does not agree

  So the gate works and the key it produced is wrong, which is what a stand-in
  has to produce: the three numbers are built from five measurements the
  program takes of its host, and this environment is not that host. The five it
  measured here were

    113219, 217419, 618090305, 1549103305, 1163791916

  and the sixth input is 1729227716, which the build carries itself, with a
  seventh fixed at 0.

  What the program measures, as it did it:

    makes a Part, parents it, turns off collision, touch and query, sets
    Transparency to 1 and Size to (1.25, 3.5, 6.25), gives it custom physical
    properties, builds a CFrame from an orientation and sets the Part's CFrame
    to it, then reads back
        AngularAccelerationToTorque
        TorqueToAngularAcceleration
        GetMass
        VectorToObjectSpace, twice
        VectorToWorldSpace, twice
    and separately GetChildren, FindFirstChild, FindFirstChildOfClass and
    FindFirstChildWhichIsA on a Model, and IsStudio, IsClient and IsServer on
    RunService.

  Every one of those is a fact about Roblox rather than about this file: a
  block's mass is its volume times its density, its inertia about an axis
  follows from its size and mass, and the two vector transforms are the part's
  CFrame applied one way and the other. So the way in is to answer them
  exactly, not to search for the key: the tag above says yes or no on each
  attempt, and a wrong answer is caught rather than accepted.

  That is where this stands. The payload is 1022 bytes, slice 4, and the 36
  string table entries no opened slice reaches belong to it.

  WHAT THE GATE'S FIVE NUMBERS DEPEND ON, MEASURED
  ------------------------------------------------
  The run was taken again 233 times, each time with exactly one host answer
  changed and nothing else, and the key the gate built was compared. That names
  the gate's inputs without reading its bytecode.

  The five numbers move when any of these change:

    UDim.Offset        14 reads
    UDim.Scale          7 reads
    Vector3.X, .Y, .Z  12 reads
    Axes.X, .Y, .Z      6 reads
    Faces.Top, .Bottom, .Back

  They do not move when the part's mass, its centre of mass, its torque
  conversions, or which side of the client/server/Studio line the script is on
  change. So the gate folds datatype algebra, not the engine's physics: every
  number in that list is a pure function of the arguments the program passed in,
  which is why this environment answers them exactly rather than by deriving
  anything.

  Nothing the program asks for is unanswered now, and no arithmetic in the run
  touches a value this environment invented. The key it builds is still rejected
  by the payload's own tag, so one of the answers above is still not what Roblox
  would say, or the program takes a different branch here than it would there.
  Two branch-level host facts were found by this method and are recorded as
  derived: the engine's AngularAccelerationToTorque and
  TorqueToAngularAcceleration are reported disabled, and whether they raise or
  answer changes the five numbers while the numbers they answer with do not.

  So the remaining work is reading the fold itself, which is now possible: slice
  3 is open, its 336 constants and 54 names are readable, and the fold is in its
  instructions.
