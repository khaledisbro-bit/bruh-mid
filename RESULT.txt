RESULT.TXT - the source code, what there is of it and what is left

THE FILE IS TWO PROGRAMS, NOT ONE

  the first slice   the measurement layer. 96,891 bytes. It asks the host
                    questions and turns the answers into three numbers.
  the second slice  the real script. 10,494 bytes. Encrypted with those three
                    numbers.
  the third slice   the string table both share.
  the fourth slice  the import list, in the open.

THE FIRST SLICE IS DONE. ALL OF IT.

Read, deserialised, and written out with its real names:

  17 functions, 96,891 of 96,891 bytes accounted for
  671 constants: 116 came out as text, 550 as numbers
  4 packed functions opened, each confirmed by the file's own tag
  SOURCE_LAYER1.txt      every function, with the names and numbers it holds
  decoy.lua              2,254 lines of Lua: what it does to the host, in order
  LAYERS.txt             all six layers and what each one gave up
  STRINGS.txt            the whole string table, 124 entries
  IMPORTS.txt            the 18 host names the interpreter reaches for

Its functions, by what they hold: one is the three number fold with nineteen
multipliers, one is a mixer, two carry digests and compare them, one builds the
GUID question, one the UDim2 question, one the newproxy question, two the refused
classes, and one drives the accumulators for 180 steps.

THE SECOND SLICE IS NOT DONE, AND HERE IS EXACTLY WHY

Its 10,494 bytes are in real.lua along with the whole tool that reads them:
decrypt, check the five magic bytes, read every function, unpack every constant,
resolve every name, open the packed functions. Set KEY at the top and it prints
the script.

The key is three numbers, and they are not in the file. They are a hash over the
answers the first slice collects, so they come out right only when every answer is
right. Seventeen of those answers are now known to be folded, and four more are
known to be read and thrown away, each settled by running the build twice and
comparing the fold chain step for step.

One answer was found wrong and fixed: typeof(Enum) is "Enums" in the host and this
file said "table". The key moved. It is still not the right key, so at least one
more answer is wrong - and the answer is somewhere in a closed list of 38 host
reads, not somewhere unknown.

host_probe.lua asks all 38 on their own and prints them one per line. Run it on a
real client, put the two lists side by side, and the first line that differs is the
last thing standing between here and the script.

THE FILE SENT BACK IS THE SAME FILE

Checked rather than assumed:

  228,754 bytes, both of them
  sha256  35b0d3c1bd0b135ed98eaceb9993a1444737e9b233324ade9f2132fbfc936b32
  md5     78f8d954315630b709bfa189b23e80bb
  byte for byte identical to the one this analysis has been working on

And the pipeline was pointed at that exact upload rather than at the copy on
disk. It runs it, reaches the second slice, and computes the same key:
2135935925, 693359311, 48315665. So every result above is a result about this
file, not about a sibling of it.

It is still the obfuscated input, not anything's output: it begins
return({[730471]=[=[ and carries one base85 body of 228,754 bytes. Whatever was
tried on it, what came back was the file itself.

WHAT A TOOL THAT READS ONE LAYER GETS

The measurement layer, and nothing else. That is not a failing of any particular
tool: the first slice is the only one that decrypts without a key, so a pass that
stops at the first serialised program it finds comes back with 2,536 instructions
that build a Folder, read a few components, ask typeof and throw most of the
answers away. It looks like the script and it is not. The script is the second
slice, and nothing reaches it without the three numbers.
