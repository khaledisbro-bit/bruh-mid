real.txt - THE RESULT
=====================================================================

THE ANSWER IN ONE LINE
---------------------------------------------------------------------
  Your script is 10494 bytes inside the file, at offset 96902 of the
  block the loader decompresses. It is encrypted. Its key is three
  numbers that are not stored anywhere: they are computed from what the
  machine answers while the decoy layer runs. The key this environment
  produces is wrong, so the script is still not readable.

WHAT IS PROVEN, NOT ASSUMED
---------------------------------------------------------------------
  The cipher. Reimplemented from the interpreter's own source and run
  against a piece whose key the file carries. It reproduces the build's
  own output byte for byte:
      piece 1, 96891 bytes, key "2111447040"
      first bytes produced here : 4d59716d65a143111b3cf7aefaaeffffaeffffae
      first bytes the build made: 4d59716d65a143111b3cf7aefaaeffffaeffffae

  The check the build runs before it decrypts. It is HMAC-SHA256 over
  the ciphertext, keyed by the salt, a zero byte, and the key material.
  Verified on the same piece:
      computed: 75a8b0d01aaea83422ca96a111793743d5596b959569f3295c6a91bb2e70e532
      in file : 75a8b0d01aaea83422ca96a111793743d5596b959569f3295c6a91bb2e70e532

  The key's own arithmetic. Five measured numbers go into three linear
  forms mod 2147483647. The five this run measured give exactly the
  three the build used:
      Si = 768435
      Sq = 553584
      SJ = 1705633901
      Se = 1508207997
      SU = 1621166966
      ->  562797805, 1581986302, 337997813

  So there is an exact offline test for any candidate key: it either
  reproduces the tag the file carries or it does not, and the answer
  takes microseconds with nothing running.

WHAT THE SEARCH SETTLED
---------------------------------------------------------------------
  Each of the five measured numbers was taken as the only wrong one and
  scanned over its whole range - 2147483647 values each, 10737418235 in
  all. A candidate was kept when its decryption looked like a program
  rather than like noise (48 uniform bytes hold about 41 distinct values;
  the piece whose plaintext is known holds 25; anything at or under 34
  was kept) and then checked against the file's own tag.

      Si   8604 candidates kept, none passed
      Sq   8557 candidates kept, none passed
      SJ   8719 candidates kept, none passed
      Se   8593 candidates kept, none passed
      SU   8566 candidates kept, none passed

  The search was tested on a key planted on purpose before its result was
  believed: it found that key, and the tag check accepted it.

  So no single wrong answer explains it. At least two of the five numbers
  are wrong together, and a joint search over two is 2^62 - out of reach.

WHERE THAT LEAVES IT
---------------------------------------------------------------------
  Everything the build double-checks about the host, this environment
  now answers correctly - which is why it gets far enough to ask for the
  encrypted piece at all, something it never did before. What is wrong is
  in answers the build folds without checking, and more than one of them.

  Two ways to the script from here, and both are real:

  1. Keep correcting the host. Every fix is measurable: change an answer,
     re-run, see whether the key moves. The remaining difference is in
     answers nothing verifies, so it has to be found by making this
     environment more like a client rather than by searching.

  2. Run harness_for_executor.lua once on a real client. It prints the
     key measured there. Put those three numbers in real.lua, run it, and
     the script writes itself out - the cipher that does it is verified
     above.

THE BYTES THEMSELVES
---------------------------------------------------------------------
  real.lua carries all 10494 of them, with the cipher, ready for the key.
